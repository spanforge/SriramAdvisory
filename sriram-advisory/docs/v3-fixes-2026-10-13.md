## Changes

- Added the optional product/website URL with HTTP(S)-only validation and a 2048-character limit.
- Added the specified situation prompt and live Unicode character counters. Required name, email, five-stage selection and privacy acknowledgement remain validated.
- Moved additional organisation/attempts/outcome fields under an optional context section.
- Added a 15-second transport timeout. Failure preserves typed content and the submission reference. Pending submissions lock controls and ignore duplicate submissions.
- Confirmation requires HTTP success and JSON `ok: true`; unexpected response bodies do not show success. Confirmation explains that scope and fee must be agreed before the review begins.
- Added privacy-safe review CTA, enquiry-start and successful-submission hooks. Only allowlisted event names and placements pass; enquiry content is never used as an event property. Query strings and fragments are removed; article slugs are redacted. Legacy assessment/payment events are ignored.
- Existing Vercel Analytics collection is opt-in with `NEXT_PUBLIC_REVIEW_ANALYTICS=1`. Enable only if the existing plan already includes custom events. No paid upgrade is required. Development and staging do not load the collector. Browser events alone do not create a durable analytics history.
- Added staging access protection with server-only `STAGING_USERNAME` and `STAGING_PASSWORD`. `SRIRAM_STAGING=1` blocks access if credentials are absent, requires authentication otherwise, and adds noindex/no-store headers. Keep `SRIRAM_STAGING=0` for production.
- Updated privacy disclosure for the URL field and optional analytics, the form operations guide and outdated browser expectations.

## Review, deployment and rollback

For local review use `npm run build -- --webpack` and `npm run start`. For hosted staging, set `SRIRAM_STAGING=1` and strong server-only staging credentials in the existing host; do not put credentials in public variables or tracked files. Publishing follows owner review of staging. Before publishing preserve the current production deployment ID and source revision. To roll back, restore that deployment using the existing host's rollback controls; leave received Formspree enquiries intact. Switching production to the new build requires `SRIRAM_STAGING=0`; verify canonicals, robots and sharing after release.
